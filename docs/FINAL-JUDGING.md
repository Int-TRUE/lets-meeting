# 최종 심사 시나리오와 데이터 재구성

2026-10-28 사용자 요청에 따라 음성 내레이션 없이 짧은 한국어 자막만 사용하는 150초 발표를 구성한다. 전산기기 교체 업무를 이어받은 담당자의 흐름을 보여주고, 화면에는 체험·시연 표식을 붙이지 않는다. 데이터는 발표를 위한 가상 업무 내용이며 실제 성과·도입 실적으로 설명하지 않는다.

업무관련성, 확산 가능성, 완성도, 창의성 및 AI 활용성은 사용자가 이전 대화에서 제공한 기준이다. 공식 배점은 확인되지 않았다. AI 활용성은 평가 항목으로만 기록하며, 이번 150초 영상에는 AI 개발 협업 장면이나 별도 AI 자막을 넣지 않는다. 자동 녹취·요약, 자동 출석 감지, 회사 SSO, 원텔 예약은 구현된 기능으로 소개하지 않는다.

예정 회의와 요약 대기 회의는 서로 다른 기록이다. 영상에서 ‘다음 회의 준비’와 ‘지난 점검 회의 정리’를 구분한다. 실제 화면 촬영은 서버에 새 데이터를 적용하고 검증한 뒤 진행한다. 실제 DM은 별도 촬영용 회의를 만들고 전달을 확인한 뒤 촬영한다. 기본 데이터의 억제 기록은 성공 발송 증거가 아니다.

### 자막과 화면 편집

- 자막은 SRT 20개 큐로 구성하고, 한 번에 짧은 1~2줄만 표시한다. 긴 설명을 읽게 하기보다 해당 화면에서 확인할 결정이나 행동 하나를 적는다.
- 클릭이나 화면 이동 후에는 결과를 읽을 수 있도록 2~3초 여백을 둔다. 자막을 바꾸는 순간에 다음 화면으로 급히 이동하지 않는다.
- 긴 구간의 끝 2초는 자막을 비워 화면을 읽게 한다. 특히 01:29–01:34의 5초는 실제 수신 DM을 자막 없이 보여준다.
- 자막이 회의명, 결정 사항, 체크 상태를 가리지 않도록 배치한다. 화면의 본문을 확대하는 장면에서는 자막을 더 짧게 줄인다.
- 내레이션 파일이나 음성 읽기 구간은 만들지 않는다. 화면의 실제 변화와 자막만으로 흐름을 이해할 수 있게 한다.

02:04–02:24는 `부서 간 운영 협의` 토픽의 기존 데이터로 설명한다. 종료된 `점검표 의견 취합` 회의에서 “초안을 검토한 뒤 최종 결정 사항을 확정합니다.”라는 결정과 후속 작업을 보여준다. 처음에는 `취합한 의견 분류`만 완료되어 있다. `참가자와 초안 검토`를 체크하여 2/3 완료로 바꾸고, `최종 결정 사항 저장`은 미완료로 남긴다. 다음 `공통 점검표 후속 협의`를 준비하기 전에 지난 회의에 남아 있는 이 작업을 확인한다. 작업의 자동 복사나 이관을 구현한 것으로 설명하지 않는다.

자막은 “이번에는 부서 간 운영 협의. / 공통 점검표의 남은 일을 확인합니다.”(2줄) → “검토를 마친 항목은 완료로.” → “다음 협의 전에, / 지난 회의의 남은 작업부터 확인합니다.”(2줄)로 연결한다. 체크 후 결과를 읽을 여백을 두고, 02:22–02:24에는 자막 없이 남은 작업을 보여준다.

## 새 데이터

`scripts/judging-dataset.mjs`의 `buildDataset({baseDate, people, rooms})`는 5개 토픽, 13개 회의, 4개 실제 첨부 파일을 반환한다. 계정 이름은 설치된 디렉터리에서 가져온다.

| 토픽                 | 회의 수 | 확인할 내용                                 |
| -------------------- | ------: | ------------------------------------------- |
| 전산기기 교체        |       5 | 과거 완료 3건, 요약 대기 1건, 다음 회의 1건 |
| CMS 서비스 점검      |       3 | 자료, 취소, 예정 회의                       |
| 부서 간 운영 협의    |       3 | 결정 사항, 저장된 요약 초안, 후속 협의      |
| 보안 점검 실무 협의  |       2 | 구성원·참가자별 조회 범위                   |
| 차세대 업무환경 개선 |       0 | 회의가 없는 토픽, 첫 회의 생성              |

메인 토픽에서 `taeheon`은 Owner, `sujin`은 Master이자 새 담당자, `wooseok`과 `jooyoung`은 Attendee다. 주시연은 `sujin`으로 진행한다. 과거 회의 한 건에는 `jooyoung`을 제외하여 참가자별 이력 차이를 확인할 수 있다.

종료된 `교체 준비 점검` 회의에는 부분 요약과 1/3 완료된 작업 목록을 준비한다. `sujin`이 결정 문장을 보완하고 `wooseok`도 참가자로서 저장할 수 있다.

- 결정: 1차 교체는 정보개발팀부터 진행한다. 다음 점검 회의에서 진행 상황을 확인한다.
- 후속 작업: 1차 교체 대상 목록 확인(완료), 정보개발팀 사전 안내(미완료), 교체 일정 등록(미완료).
- 촬영 중 사전 안내를 체크한 뒤 재조회하여 2/3 완료가 유지되는지 확인한다.

분당의 기존 회의실을 유지하고 4층 회의실 A(8명), 4층 회의실 B(12명), 5층 대회의실(20명)을 추가한다. 추가 방의 층·정원은 사용자가 구체적 정보를 제공하지 않아 정한 가상 데이터 값이다. 기존 ID가 같은데 내용이 다르면 덮어쓰지 않고 중단한다.

## 서버 적용 범위

`scripts/replace-judging-data.py`는 기존 자체 서버의 `./butler`와 컨테이너 안의 Node/PostgreSQL만 사용한다. Python 3 표준 라이브러리로 실행되며 앱 이미지와 환경설정을 교체하지 않는다.

**사용자 승인 범위:** 모든 토픽·회의·참가 관계·첨부·요약·후속 작업·기존 발송 기록·요청 중복 방지 기록을 교체한다. 계정, 개인 설정, 기존 회의실, DB 메타데이터는 보존한다. 이미 Mattermost에 도착한 메시지는 이 데이터베이스와 별개이며 삭제하지 않는다.

기본 실행은 조회와 계획만 수행한다. `--apply`에서만 앱을 잠시 중지하고 다음 순서로 실행한다.

1. 스키마·현재 자료의 지문을 확인하고, 계획 이후 변경이 있으면 중단한다.
2. 설치 폴더의 형제 위치 `.robot-butler-judging-backups/<시간>/`에 전체 DB를 비공개 권한으로 백업한다. 백업 목록 검사가 실패하면 삭제하지 않는다.
3. DB 잠금과 단일 트랜잭션 안에서 기존 활동 자료를 교체하고 분당 회의실을 추가한다.
4. 계정·설정·기존 회의실·메타데이터 보존, 첨부 바이트, 참조 관계, 삽입 내용을 확인한다.
5. 기존 앱을 시작하고 실제 health·디렉터리 조회와 DB를 다시 검사한다. 실패하면 백업 복구를 시도하고 검증 결과를 명시한다.

예정 회의의 시작·종료·리마인드 처리는 `suppressed:judging-fixture`로 명시적으로 억제한다. 발송 성공 기록은 만들지 않는다. **일정을 수정하거나 새 회의를 만들면 정상 알림이 발생할 수 있다.** 실제 알림 촬영은 수신 대상과 시간을 정한 별도 단계에서 수행한다.

## 실행

서버 SSH 접속과 아래 명령 실행은 사용자가 직접 진행한다. 서버 적용 결과를 확인한 뒤 실제 화면을 촬영하며, 파일 준비나 로컬 검증만으로 서버 적용·촬영이 완료된 것으로 보고하지 않는다.

두 파일을 같은 폴더에 둔다. 기본 앱 경로는 `/home/mattermost-admin/robot-butler-direct-20261026`, 기본 확인 주소는 `https://kftc-robot-butler.tailba32fb.ts.net:8443`이다. 설치 위치가 다르면 `--app-dir`, 주소가 다르면 `--base-url`을 지정한다.

```bash
# 기본: 읽기 전용 계획. 기준일은 실행 시점의 서울 날짜.
sudo python3 replace-judging-data.py

# 백업 후 사용자 승인 범위 전체 교체.
sudo python3 replace-judging-data.py --apply
```

일자와 검토한 계획을 고정하려면 다음을 사용한다. 입력한 기준일을 바꾸면 계획을 새로 만든다.

```bash
sudo python3 replace-judging-data.py --base-date 2026-10-28 --summary plan.json
sudo python3 replace-judging-data.py --base-date 2026-10-28 --expect-plan plan.json --apply
```

`status: verified`와 백업 경로를 확인한 뒤 브라우저를 새로고침한다. 실패한 결과를 성공으로 간주하지 않는다. SSH 인증이 없는 환경에서는 이 파일을 준비한 것만으로 서버에 반영된 것이 아니다.

## 복구

출력된 실제 백업 폴더를 사용한다. 복구 전 현재 DB도 별도로 백업하므로 교체 이후의 작업을 보존할 수 있다. 복구는 해당 시점의 전체 DB로 돌아가므로 이후 계정·회의실 변경도 함께 되돌아갈 수 있다.

```bash
sudo python3 replace-judging-data.py --rollback /home/mattermost-admin/.robot-butler-judging-backups/<출력된시간>
```

백업·상태 파일에는 비공개 데이터가 포함될 수 있다. Git, 배포 묶음, 대화에 올리지 않는다.
