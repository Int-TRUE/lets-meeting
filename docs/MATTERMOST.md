# 매터모스트 로컬 DM 시연

2026-10-24 사용자 요청: Mac Docker의 매터모스트에 로봇집사 회의 생성·변경·취소를 참가자별 DM으로 자동 전송한다. 로봇집사도 같은 Mac에서 `npm run dev`로 실행한다.

## 구성

- 로봇집사: http://localhost:5173 / SQLite
- Mattermost: http://localhost:8065 / 전용 PostgreSQL / Docker 볼륨
- 봇은 일반 사용자 권한이다. 회사 계정/SSO 인증을 구현한 것은 아니다.
- `.env.local`의 서버 전용 변수로 활성화한다. `VITE_` 접두사를 사용하지 않는다.
- `MATTERMOST_ENABLED=true`, `MATTERMOST_URL`, `MATTERMOST_BOT_ID`, `MATTERMOST_BOT_TOKEN`, `MATTERMOST_USER_MAP`(직원 ID → Mattermost 사용자 ID JSON), `ROBOT_BUTLER_URL`을 설정한다.
- 토큰·계정 비밀번호·매핑 파일은 Git에서 제외한다. URL은 HTTPS 또는 로컬 HTTP만 허용한다. 외부 응답·인증정보는 발송 이력에 남기지 않는다.
- 시연 참가자 24명은 각각 별도 계정에 연결한다. 정금결은 사용자가 지정한 기존 관리자 계정에 연결하고, 나머지는 로컬 시연 전용 계정을 사용한다. 다른 사람의 알림을 관리자 한 명에게 몰아 보내지 않는다.

## 동작과 실패 처리

회의 변경과 참가자별 이벤트를 같은 DB 트랜잭션으로 저장한다. 커밋 후 대기 이벤트를 선점해 DM을 전송한다. 네트워크 요청 중 DB 잠금을 유지하지 않는다. 생성 요청 키·수정 revision 검증으로 중복 이벤트를 막고, 같은 프로세스의 이벤트 배치를 순서대로 처리한다.

- 생성: 생성자 포함 참가자 전원.
- 변경: 현재 참가자에게 이전/이후 제목·일시·장소. 제외된 참가자에게는 이전 회의 제목과 제외 안내만 제공하며 새 일정·링크를 보내지 않는다.
- 취소: 현재 참가자에게 취소 안내.
- 본문에는 한국 시간과 권한 검사를 거치는 회의 상세 링크를 포함한다. 사용자 입력의 Markdown과 @멘션은 이스케이프한다.
- 회의 저장 성공과 DM 발송 성공을 분리한다. 실패해도 저장된 회의를 되돌리거나 중복 생성하지 않는다.
- 상태: 미연결 / 대기 / 전송 중 / 완료 / 실패 / 결과 확인 필요. 계정 미연결·인증 오류는 실패로, POST 타임아웃·서버 오류 등 전달 여부가 불명확하면 결과 확인 필요로 기록한다.
- 재시도 정책은 아직 미정이다. 자동·수동 재전송을 제공하지 않는다. 재시작 시 대기 건은 전송하고 전송 중이었던 건은 결과 확인 필요로 변경한다. 외부 전송과 DB 기록 사이에 프로세스가 종료되면 정확히 한 번 전송을 보장할 수 없으므로 실제 DM 확인이 필요하다.
- 연동 전의 과거 미전송 이벤트는 소급 발송하지 않는다. 자료·요약·리마인드는 이번 범위에 포함하지 않는다.
- 관리자 이력 API는 메시지 스냅샷을 제외한다. 회의 발송 요약은 해당 회의 열람 권한을 확인한 후 집계만 반환한다.

## 배포 범위

Vercel은 Mac의 `localhost`에 직접 접속하지 않는다. 사용자 요청으로 추가한 중계 모드에서는 Vercel이 회의와 발송 대기를 같은 트랜잭션에 저장하고, Mac이 HTTPS로 가져와 로컬 Mattermost에 전송한다. 외부 공개나 터널은 필요 없다. 공개 테스트 계정 선택은 회사 인증이 아니므로 서버의 수신자 허용 목록과 Mac의 별도 계정 매핑에 있는 시연 계정만 전송한다. 봇 토큰은 Mac에만 둔다.

## 검증

`npm run check`는 실제 DM 없이 격리된 검사다. SQLite 전송기 검사는 생성·수정·취소, 중복 요청, 권한 거부, 미연결 수신자, HTTP 실패, 전송 결과 불확실성, 재시작 복구를 검증한다. 실제 시연은 별도 테스트 Topic과 미래 회의를 만들어 참가자별 DM 및 발송 이력을 확인한다.

## 배포 앱 → 맥 중계 프로그램

### 시연 시작과 종료

현재 시연 구성은 Docker Desktop의 `robot-butler-mattermost` 그룹 아래 `postgres`, `mattermost`, `relay` 세 컨테이너다. **Docker Desktop을 시작하면 세 컨테이너가 자동으로 다시 시작된다.** 수동으로 정지한 상태에서 Docker를 계속 실행 중이라면 그룹의 시작 버튼을 누른다. 컨테이너를 삭제한 경우에는 아래 시작 파일로 다시 생성한다. 볼륨은 삭제하지 않는다.

1. 처음 설치하거나 코드를 갱신한 뒤에는 프로젝트의 `start-mattermost-demo.command`를 더블 클릭한다. Docker Desktop을 열고 세 컨테이너를 생성·갱신한다. Mac에 Node.js를 별도로 실행할 필요가 없다.
2. Docker Desktop에서 `relay`가 실행 중이고 건강 상태가 healthy인지 확인한다. 정상적인 인증·서버 조회에 성공하면 건강 상태가 갱신된다. 시작 직후에는 starting으로 표시될 수 있다.
3. https://robot-butler.vercel.app 에서 회의를 생성·변경·취소한다. http://localhost:8065 의 `robot-butler` DM에서 확인한다. 정금결은 `jeong` 계정이다. 발송 결과는 회의 화면의 새로고침으로 확인한다.
4. 시작 파일의 터미널 창은 닫아도 된다. 종료하려면 Docker Desktop에서 그룹 전체를 정지하거나 Docker Desktop을 종료한다. Mac의 잠자기·덮개 닫힘 상태에서는 중계도 중단되므로 시연 중에는 맥을 깨어 있게 둔다.

Docker의 `restart: always` 정책을 사용하므로 수동 정지한 컨테이너도 다음 Docker 재시작 때 다시 시작된다. macOS 로그인 시 Docker 자체를 자동 실행하는 설정까지 변경한 것은 아니다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/) 참고.

구성은 비공개 `.env.mattermost-local/compose.yaml`에 저장된 기존 서버 설정과 `docker/mattermost-relay/compose.yaml`의 중계 설정을 함께 사용한다. 발송 기록은 `robot-butler-mattermost_relay_state` Docker 볼륨에 유지한다. 이미지에는 두 개의 실행 소스와 package.json만 포함하고 비밀값은 실행 시 주입한다. 외부 포트와 Docker 소켓을 중계기에 공개하지 않는다.

개발용으로 `npm run mattermost:relay`도 남아 있지만 Docker 중계기와 동시에 실행하지 않는다. 컨테이너와 호스트의 발송 기록은 서로 다른 저장소이며, 전환 시 기존 중계기를 먼저 정상 종료하고 기록을 이관해야 한다. 기존 Mac 기록은 `data/relay-production.sqlite`에 보존한다.

### 설정

- Vercel의 기존 robot-butler 프로젝트: `MATTERMOST_RELAY_ENABLED=true`, `MATTERMOST_RELAY_TOKEN`(무작위 32바이트의 64자리 hex), `MATTERMOST_RELAY_RECIPIENTS`(허용된 직원 ID를 쉼표로 연결). Production과 Preview의 인증값은 서로 다르게 설정한다. Preview는 해당 작업 브랜치에만 설정한다.
- Mac의 Git 제외 파일 `.env.mattermost-local/relay.env`: 위 토큰과 `MATTERMOST_RELAY_ORIGIN=https://robot-butler.vercel.app`, `MATTERMOST_ENABLED=true`, 기존 봇 ID/토큰·서버 URL·사용자 매핑·`ROBOT_BUTLER_URL`을 설정한다. 파일 권한은 소유자 읽기/쓰기(600)로 제한한다. 중계기는 상세 링크를 중계 대상 origin으로 고정한다.
- 봇 토큰·사용자 매핑·DB 접속 정보는 중계 요청에 포함하지 않는다. 중계 전용 토큰은 브라우저에 전달하지 않는다. `/api/mattermost-relay`의 claim/ack만 전용 토큰으로 접근한다.
- 이 기능을 끄려면 서버의 활성화 변수를 false로 바꾸고 재배포한다. 인증값 교체 시 서버와 Mac 설정을 함께 갱신한다. 일반 다른 Preview에는 중계를 활성화하지 않는다.

### 대기와 복구

- 평상시 약 5초마다 확인하고, 대기 작업이 있으면 연속으로 처리한다. 네트워크 실패 시 최대 30초 간격으로 재접속한다.
- Mac·Docker가 꺼져 있으면 아직 가져가지 않은 알림은 서버에 대기한다. 재실행 시 순서대로 처리한다. 미연결 상태로 기록된 과거 알림은 소급 발송하지 않는다.
- 서버 DB 잠금으로 한 번에 한 작업만 선점한다. 여러 중계기가 실행돼도 동일 작업을 동시에 가져가지 않는다. 선점 응답을 잃으면 같은 요청 ID로 복구한다.
- 중계기 SQLite 기록(Docker 볼륨)에 발송 시도 전 상태와 발송 후 결과를 저장한다. 결과 보고가 실패하면 결과만 다시 올리며 DM은 재전송하지 않는다.
- DM 전송 중 종료·타임아웃처럼 실제 도착 여부를 확정할 수 없으면 `결과 확인 필요`로 기록한다. 2분간 결과가 없는 선점은 다음 조회 때 같은 상태로 전환한다. 자동 재전송하지 않으므로 실제 DM 확인이 필요하다. 이는 외부 전송과 DB 기록 사이의 장애로 인한 중복을 피하기 위한 처리다.
- 생성·변경·취소만 지원한다. 자료·요약·리마인드와 실패 DM의 수동 재전송은 기존 미정 정책을 유지한다.

## 회의 시작·지각 응답·회의실 연장

Docker 중계기가 가동되는 동안 서버를 약 5초 간격으로 조회하여 다음 시각 알림을 예약한다. 별도 클라우드 예약 작업은 필요 없다. Mac이 꺼지거나 잠자기 상태이면 즉시 발송할 수 없다. 시작 후 5분이 지난 과거 시작 안내와 종료된 회의의 안내는 새로 생성하지 않는다.

- 시작 시 생성자 DM의 **지각자 선택하기** → 여러 참가자 선택 → **알림 보내기**. 동일 회의 시작 시각·참가자마다 한 번 발송한다.
- 지각자 DM의 응답 메뉴에서 출발·먼저 시작·불참 중 하나를 선택하면 생성자에게 이름과 응답을 DM으로 보낸다. 응답은 해당 알림당 한 번만 확정한다.
- 종료 5분 전 생성자에게 텍스트 안내와 가능한 **30분/60분 연장하기** 버튼, **회의 변경 페이지** 링크를 제공한다. 불가능한 연장 시간은 예약·운영시간 제한 문구로 표시한다. Mattermost 기본 액션의 비활성 속성에 의존하지 않는다.
- 연장 클릭 시 서버 트랜잭션에서 생성자, 현재 회의 상태, 원래 종료 시각, 충돌, 09~18시 운영 범위를 재검사한다. 성공하면 참가자에게 변경 알림을 보낸다. 같은 알림을 반복 클릭해도 한 번만 연장한다. 새 종료 5분 전에는 새 안내를 보낼 수 있다.
- 진행 중 회의의 변경 페이지에서는 시작·회의실을 유지하고 현재 이후의 종료 시각을 선택할 수 있다. 일반 수정 권한과 revision 검사는 유지한다.

현재 Mattermost 11.7의 interactive dialogs `multiselect`와 attachment actions를 사용한다. 콜백은 Compose 내부 `http://relay:8066`에만 연결하고 호스트 포트를 공개하지 않는다. `AllowedUntrustedInternalConnections`는 정확히 `relay`만 허용한다. 요청은 수신자·동작·만료 시각을 묶은 HMAC 티켓과 원본 봇 메시지를 검증한 뒤, 서버가 회의 권한을 다시 확인한다. 클라우드에는 기존 중계 Secret만 사용하며 봇 토큰은 Mac에 남는다.

생성·변경·취소·지각 배너는 `public/notification-banners/comic-v2/`의 손그림 JPEG 4개(각 약 60~75KB, 720×240)다. 개인 정보가 없는 공통 이미지이며 배포 주소에서 제공한다. 시작 확인·종료 안내·응답 회신은 텍스트다. 이미지를 보지 못하는 클라이언트에도 회의 정보와 안내가 텍스트로 남는다. 시각은 한국 시간, 분 단위로 표시한다.

검증: 권한·서명 변조·중복·시간 창·충돌·운영시간 단위 검사, 실제 로컬 Mattermost의 복수 선택 창·두 참가자 DM·응답 회신·30분 연장과 참가자 변경 DM을 격리된 SQLite 회의로 확인했다. 테스트에서만 시계를 주입하며 배포 API에는 시간 변경 입력이 없다.
